# 抢占与唤醒

> 判据负责"该不该换"，本篇负责"什么时候提出换"。上一节讲 `pick_eevdf()` 怎么选，这一节讲谁、在什么条件下触发它。

## 1. 它解决什么问题

EEVDF 的合格判据只回答"谁有资格跑"。但内核还要回答另一个问题：**正在跑的任务要不要被打断？**

场景很具体。任务 A 在 CPU 上跑，任务 B 被唤醒（可能是生产者刚交了数据）。此时有三种做法：

- 立刻抢占 A，让 B 上——响应快，但如果 B 只是短暂唤醒，切换开销白花
- 等 A 的时间片用完——省开销，但响应慢，可能拖几十毫秒
- 让 `pick_eevdf()` 结合保护窗口判断——折中

`wakeup_preempt_fair()` 做的就是这件事：**用一组廉价条件快速排除不该抢的情形，剩下的交给挑选逻辑定夺**。它不是"抢占判断"，更像"抢占筛选"。

## 2. 接口变迁：这一整层都改名了

这是本篇读代码最意外的发现。经典教材里的函数名在 7.4 里**一个都找不到**：

| 5.x 的写法 | 7.4 的现状 |
| --- | --- |
| `sched_class.check_preempt_curr` | 改名为 `wakeup_preempt`，签名 `(rq, p, flags)` |
| `check_preempt_wakeup()` | 改名为 `wakeup_preempt_fair()` |
| `wakeup_preempt_entity()` | **不存在**，逻辑融入 `wakeup_preempt_fair` + `pick_eevdf` |
| `sysctl_sched_wakeup_granularity` | 不再用于唤醒抢占判断 |
| `resched_curr()` | 唤醒路径改用 `resched_curr_lazy()` |

同时 `sched_class` 里几个动作签名也变了：

```c
void (*wakeup_preempt) (struct rq *rq, struct task_struct *p, int flags);
struct task_struct *(*pick_task)(struct rq *rq, struct rq_flags *rf);
void (*put_prev_task)(struct rq *rq, struct task_struct *p, struct task_struct *next);
void (*set_next_task)(struct rq *rq, struct task_struct *p, enum snt_e type);
```

`pick_task` 取代 `pick_next_task`、`put_prev_task` 多带 `next` 参数、`set_next_task` 多带一个枚举——**这几个签名变化，比任何流程描述都更早暴露了实现的换代**。按 5.x 资料找这些函数，会白费很久。

## 3. 四档动作

决策结果不是布尔值，是一个枚举：

```c
enum preempt_wakeup_action {
	PREEMPT_WAKEUP_NONE,	/* No preemption. */
	PREEMPT_WAKEUP_SHORT,	/* Ignore slice protection. */
	PREEMPT_WAKEUP_PICK,	/* Let pick_eevdf() decide. */
	PREEMPT_WAKEUP_RESCHED,	/* Force reschedule. */
};
```

四档的含义差异很关键：

| 动作 | 语义 |
| --- | --- |
| `NONE` | 不抢占，当前任务继续 |
| `SHORT` | **忽略当前任务的 slice 保护**，允许挑选逻辑提前换人 |
| `PICK` | 正常调用挑选逻辑，保护仍然生效 |
| `RESCHED` | 直接置重调度标志，不查挑选逻辑 |

`SHORT` 是 EEVDF 时代的新玩意儿。它的用意是：如果被唤醒的任务时间片很短，为了不让它等一整个保护窗口，可以**放宽保护**——但依然要过合格性检查（见第 7 节）。

## 4. 决策阶梯

`wakeup_preempt_fair()` 按顺序做排除，每一步都有明确理由：

**第一步：硬性排除**

```c
if (p->sched_class != &fair_sched_class ||
    donor->sched_class != &fair_sched_class)
	return;
if (unlikely(se == pse))
	return;
if (task_is_throttled(p))
	return;
```

不同调度类不走这里；唤醒自己（`se == pse`）无意义；被 throttle 的任务不该抢。

**第二步：已有人要求重调度就不重复处理**

```c
if (!sched_feat(PREEMPT_SHORT) && test_tsk_need_resched(rq->curr))
	return;
```

注释写明理由：防止把 `curr` 误认成 buddy。只有开 `PREEMPT_SHORT` 才允许继续，因为那个特性需要覆盖已有请求。

**第三步：总开关与 idle 优先**

```c
if (!sched_feat(WAKEUP_PREEMPTION))
	return;

cse_is_idle = se_is_idle(se);
pse_is_idle = se_is_idle(pse);
if (cse_is_idle && !pse_is_idle)
	goto preempt;
```

`WAKEUP_PREEMPTION` 关闭则整条路径失效（服务器调优常用）。当前是 idle 实体而唤醒的不是——**立刻抢，不用犹豫**：idle 没有工作可保护。

**第四步：更新记账后再判断**

```c
update_curr_fair(rq);
if (cse_is_idle != pse_is_idle)
	goto update;
```

先 `update_curr_fair()` 把当前任务的 `vruntime` 推进到此刻，否则后面所有比较用的都是过期数据。idle 状态不一致（当前非 idle、唤醒的是 idle）则走 `update` 分支——没必要为一个 idle 任务抢占。

**第五步：策略与延迟出队的排除**

```c
if (unlikely(!normal_policy(p->policy)))
	goto update;
if (pse->sched_delayed)
	goto update;
```

`BATCH` 和 `IDLE` 策略的任务不抢占别人——这是它们的设计意图。第二行更值得记，注释写得很直白：

> *Do not preempt for tasks that are `sched_delayed` as it would violate EEVDF to forcibly queue an ineligible task.*

**`sched_delayed` 的任务不能通过抢占被重新入队**，否则等于绕过合格性检查，直接破坏 EEVDF 的前提。

**第六步：短时间片放宽保护**

```c
if (sched_feat(PREEMPT_SHORT) && (pse->slice < se->slice)) {
	preempt_action = PREEMPT_WAKEUP_SHORT;
	goto pick;
}
```

唤醒者时间片更短，允许覆盖保护窗口。这是"延迟优先"的体现：短任务等不起。

**第七步：fork 不触发唤醒抢占**

```c
if (wake_flags & WF_FORK)
	goto update;
```

注释理由：fork 后通常跟着 exec，共享数据的可能性低，提前抢占的收益不足以抵消切换成本。

**第八步：提名 buddy**

```c
if (sched_feat(NEXT_BUDDY) && set_preempt_buddy(cfs_rq, pse)) {
	if (wake_flags & WF_SYNC)
		preempt_action = preempt_sync(rq, wake_flags, pse, se);
}
```

## 5. buddy：一个跨唤醒的提示

`cfs_rq->next` 是"下次优先考虑谁"的提示，`pick_eevdf()` 里会先看它（第 6 节讲过）。这里决定要不要更新这个提示。

```c
static inline bool set_preempt_buddy(struct cfs_rq *cfs_rq, struct sched_entity *pse)
{
	if (cfs_rq->next && entity_before(cfs_rq->next, pse))
		return false;

	set_next_buddy(cfs_rq, pse);
	return true;
}
```

**已有 buddy 且它的 deadline 更早，就不换。** 注释解释了这个取舍：

> *The older buddy may be cache cold and completely unrelated to the current wakeup but that is unpredictable where as obeying the deadline is more in line with EEVDF objectives.*

老 buddy 可能缓存已经凉了、和本次唤醒毫无关系；但这不可预测，而**遵守截止期是可预测的**。既然 EEVDF 的目标就是按截止期排,那就按截止期办，不为"猜哪个更可能 cache hot"破坏规则。

`set_short_buddy()` 是另一套排序：先比 `slice` 长短，相同再比 deadline。因为它服务于 `PREEMPT_SHORT` 场景，标准要跟着那个场景走。

## 6. preempt_sync：给 WF_SYNC 一个阈值

`WF_SYNC` 表示唤醒者打算马上去睡（典型的生产者-消费者）。这种提示不该无条件服从，源码注释也承认 *"it is not strictly obeyed"*。

```c
threshold = sysctl_sched_migration_cost;
delta = rq_clock_task(rq) - se->exec_start;
if ((s64)delta < 0)
	delta = 0;

if (wake_flags & WF_RQ_SELECTED)
	threshold >>= 2;

if (entity_before(pse, se) && delta >= threshold)
	return PREEMPT_WAKEUP_RESCHED;
```

两个判据同时成立才强制抢占，外加一条时间门槛：

1. `entity_before(pse, se)` —— 唤醒者的 deadline 更早
2. `delta >= threshold` —— 当前任务已经跑了足够久（超过迁移成本量级）

第二条是精髓：**如果当前任务刚上 CPU，为它花一次切换不划算**，让唤醒者等一会儿。`WF_RQ_SELECTED` 时阈值除以 4，因为那意味着两个任务挤在一个 CPU 上、本来可以分散，此时更该让唤醒者优先。

## 7. 与挑选逻辑的衔接

`pick` 段：

```c
if (cfs_rq->h_nr_queued) {
	nse = pick_next_entity(rq, preempt_action != PREEMPT_WAKEUP_SHORT);
	if (unlikely(!nse))
		goto pick;

	if (nse == pse)
		goto preempt;
}

if (preempt_action == PREEMPT_WAKEUP_SHORT && entity_eligible(cfs_rq, pse))
	goto preempt;
```

注意传进去的第二个参数是 `protect = (action != SHORT)`：**只有 `SHORT` 时才关掉保护**，其余情况保护照常生效。这就是第 3 节那张表里"忽略 slice 保护"的具体落点。

然后两道放行条件：

- **挑出来的就是唤醒者**（`nse == pse`）→ 抢占。判据已经认可它了
- **`SHORT` 且唤醒者合格** → 抢占。即使没被挑中，只要合格也让它上，避免短任务等太久

`update` 与 `preempt` 两个出口：

```c
update:
	if (sched_feat(RUN_TO_PARITY))
		update_protect_slice(cfs_rq, se);
	return;

preempt:
	cancel_protect_slice(se);
	if (preempt_action == PREEMPT_WAKEUP_SHORT)
		set_short_buddy(cfs_rq, pse);
	resched_curr_lazy(rq);
```

不抢占时，`RUN_TO_PARITY` 打开会刷新保护窗口（跑到与队伍持平）；抢占时先**取消**当前实体的保护（`cancel_protect_slice` 把 `vprot` 拉到当前 `vruntime`，保护立即失效），再置重调度标志。

用的是 `resched_curr_lazy()` 而不是 `resched_curr()`——**懒抢占**：只打标记，真正切换推迟到下一个安全点（返回用户态、开抢占、显式中断点）。目的是缩短抢占延迟的同时避免在敏感位置强行切换。

## 8. rq->donor 是什么

代码里取的是 `rq->donor` 而非 `rq->curr`：

```c
struct task_struct __rcu	*donor;  /* Scheduling context */
```

`sched.h` 另一处注释说明正常情形下 `rq->curr == rq->donor == p`。两者分离属于 proxy execution 与 sched_ext 的场景（`SCX_RQ_PROXY_PENDING` 等标志）。

**这块我只确认了字段与注释，没追语义链路**，标 `推测待验证`。但它提示一件事：读抢占代码时看到 `donor` 不要当成 `curr` 的别名，在特殊配置下它们真的会不同。

## 10. 验证手段

```bash
# 看当前有哪些特性开关是开的
grep -E "WAKEUP_PREEMPTION|NEXT_BUDDY|PREEMPT_SHORT|RUN_TO_PARITY" /proc/sched_debug
```

观察唤醒抢占的真实效果，最直接的是上下文切换计数：

```bash
pidstat -w 1 5          # cswch/s 自愿切换，nvcswch/s 非自愿切换
```

`nvcswch/s` 高说明任务被强制打断得多。可以对比两种场景：

```bash
# 场景 A：生产者消费者，配合良好
# 场景 B：把 WAKEUP_PREEMPTION 关掉（需 root，仅测试环境）
echo NO_WAKEUP_PREEMPTION > /sys/kernel/debug/sched/features
```

关掉后 `nvcswch/s` 应显著下降，同时交互延迟上升——这就是那个开关的取舍。

`perf sched` 也能看单次唤醒的决策结果：

```bash
perf sched record -- sleep 3
perf sched latency
```

## 11. 结论

标注：`已核对源码（7.4.0）` / `推测待验证`。

### 11.1 这一层整体改名，5.x 资料会失效

**已核对源码（7.4.0）。** `check_preempt_curr`、`check_preempt_wakeup`、`wakeup_preempt_entity` 在 7.4 中均不存在；对应物是 `wakeup_preempt` 接口与 `wakeup_preempt_fair()`。`pick_next_task` 也改名为 `pick_task`。

### 11.2 决策结果是四档枚举，不是布尔值

**已核对源码（7.4.0）。** `PREEMPT_WAKEUP_NONE / SHORT / PICK / RESCHED`，四档在 `pick` 与出口处的处理各不相同。

### 11.3 `sched_delayed` 的任务不能靠抢占重新入队

**已核对源码（7.4.0）。** 注释原文：*"Do not preempt for tasks that are sched_delayed as it would violate EEVDF to forcibly queue an ineligible task."* 这是合格性约束在抢占路径上的延伸。

### 11.4 buddy 保留遵循 deadline 而非缓存热度

**已核对源码（7.4.0）。** `set_preempt_buddy()` 在已有更早 deadline 的 buddy 时返回 `false`，注释明确说明用可预测的 deadline 规则替代不可预测的 cache hot 猜测。

### 11.5 WF_SYNC 有条件服从，时间门槛是关键

**已核对源码（7.4.0）。** `preempt_sync()` 以 `sysctl_sched_migration_cost` 为阈值，比较当前实体已运行时长 `delta`，`WF_RQ_SELECTED` 时阈值除以 4。

### 11.6 抢占路径用懒重调度

**已核对源码（7.4.0）。** 出口调用 `resched_curr_lazy(rq)`，而非 `resched_curr()`。延迟到安全点的具体机制属`推测待验证`。

### 11.7 rq->donor 与 rq->curr 在特殊配置下不同

**字段与注释已核对源码（7.4.0）**，语义链路属`推测待验证`。
